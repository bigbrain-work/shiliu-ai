# Shiliu AI: Agent installation guide

Canonical URL: https://bigbrain.work/shiliuAI/install.txt

## Interface overview

Audience: the current Agent, using the capabilities of its client and local environment.

Purpose: guide the Agent through Shiliu MCP installation, CLI updates, WeChat authorization, client configuration, connection verification, and recovery from an existing connection failure.

Interface type: a public, read-only plain-text guide fetched from the canonical URL above. Reading it requires no login and works before MCP connects. The Agent performs the applicable commands or documented client actions under the user's authorization, then checks and reports their results.

| When to read this interface | Where to start |
| --- | --- |
| First-time Shiliu MCP setup | Steps 1-6: identify capabilities, install, authorize, configure, and verify. |
| Update an existing Shiliu CLI | Step 2, then Step 6. Preserve valid login, existing configuration, and unrelated settings; do not repeat Skill installation solely to update the CLI. |
| Connection closed, initialize timeout, or another MCP connection failure | Section 7: establish the failed stage and actual launch context before choosing a remedy. |
| Login completed but tools are absent, or the Agent has not loaded the connection | Section 7, then Step 6: check login/remote state, enable/trust/reload state, and native tool discovery. |

How to use: read this guide, select the scenario and capability branch that match the current evidence, execute only the applicable steps, and report what was actually verified. A completed terminal check, pending login, and an Agent-connected MCP are separate states.

Use this guide only for user-authorized installation, CLI updates, or connection recovery. Follow Steps 1-6 for a new setup and resume at the failed stage after repair. Do not infer installation steps from the product homepage. Never request credentials or place tokens in commands, code, Git, Agent configuration, logs, or replies. The CLI owns credential storage.

If an existing MCP connection fails, go directly to Section 7 (Diagnose and recover a failed connection). It is available through this public guide even when MCP cannot initialize. These instructions address the current Agent by capability and apply across clients; do not assume a particular vendor, configuration location, or runtime.

## 1. Check the environment

Identify the current Agent, shell, and runtime that will launch MCP. The CLI and MCP process must share the same OS user and credential store. Classify by capability, not by guessing a vendor-specific configuration file:

| Layer | Client capability | Supported path |
| --- | --- | --- |
| A | Remote HTTP MCP with a Shiliu-supported interactive authorization flow | Use the published HTTP MCP instructions; no local Node is required. This flow is not yet offered by this guide, so do not invent a URL or OAuth procedure. |
| B | Local stdio MCP and a supported writable configuration | Use the built-in `shiliu install` adapter. |
| C | Local stdio MCP configured only through a GUI or an unknown format | Generate candidates, run `shiliu doctor`, and give the user a field-by-field GUI configuration. |
| D | No MCP support, but commands and Skill instructions are available | Use `shiliu tools --json` and `shiliu call`; never build a custom JSON-RPC client. |
| E | Neither MCP nor local command execution | Report that the current client is unsupported until Layer A is available. |

Only the configuration-writing step is vendor-specific. Built-in adapters remain limited to Codex, Claude Code, and Cursor; all other clients follow the capability branches above. Do not edit Chromium/Electron LevelDB or SQLite application storage and do not infer a client capability from its implementation framework.

For Skill scope, use the requested scope. Otherwise use a persistent project root, or user scope if no project exists. Avoid temporary directories.

Run one command per invocation and check each exit code:

```text
node --version
npm --version
```

Layers B-D require the Shiliu CLI and Node.js 18.14.1 or newer. Installing or refreshing the Skill also uses the current `skills` CLI, which requires Node.js 22.20.0 or newer. Therefore require Node.js 22.20.0 or newer for the complete Skill-enabled flow. If Node/npm is missing or older, use the official Node.js 24 LTS installer at https://nodejs.org/en/download, reopen the terminal, and recheck. The installers below upgrade npm versions older than 8 to npm 9.9.4. Preserve the current PATH; shell changes may not persist between Agent commands.

An application-bundled Node runtime is not automatically a persistent system runtime. A path under an application sandbox, temporary directory, or content-addressed hash may disappear after an application update. Prefer an official system Node installation for Layers B-D; do not silently copy an application-private absolute path into MCP configuration.

Node.js 18.14.1-22.19 may be used only for CLI-only repair when the Skill is already installed and no `skills` command will run. Do not describe that limited state as a complete Agent installation.

## 2. Install CLI

Choose exactly one matching installer.

macOS/Linux or Windows Git Bash:

```sh
curl -fsSL https://bigbrain.work/shiliuAI/install.sh | sh
```

Windows PowerShell:

```powershell
irm https://bigbrain.work/shiliuAI/install.ps1 | iex
```

Require the installer's `CLI installed.` message and verify separately:

```text
shiliu --version
```

Require CLI 1.3.11 or newer for this guide's independent diagnostics and targeted repair. Existing built-in Layer B configurations remain compatible with 1.3.7 or newer, but update before following this complete guide. If `shiliu` is blocked by PowerShell execution policy, use `shiliu.cmd` in that PowerShell session. If the command is missing, resolve the npm global executable location without replacing the runtime's PATH. CLI installation alone does not complete MCP setup. The installer requires an actual npx initialize + tools/list handshake before reporting success; three bootstrap tools are sufficient without login. --version is lightweight and does not establish dependency integrity.

## 3. Install Skill

Select only the current client. Skill installer identifiers and Shiliu CLI identifiers are not always the same:

| Client | SKILL_AGENT | MCP_AGENT |
| --- | --- | --- |
| Codex | codex | codex |
| Claude Code | claude-code | claude |
| Cursor | cursor | cursor |

For another client, use only a Skill identifier documented by that client or by the current `skills` CLI; never guess one. Install the Skill with that `SKILL_AGENT` and record the exact refresh target. Choose `project` unless the user requested user scope or there is no persistent project:

```text
shiliu skill install --agent SKILL_AGENT --scope project --json
shiliu skill install --agent SKILL_AGENT --scope user --json
```

Run exactly one of those commands. For project scope, run it from the chosen project root. The CLI invokes the website Skill source, needs neither Git nor GitHub, and records the Agent, scope, root, and installation path used by future `shiliu skill refresh` calls. Read `installPath` and `refreshTargetRecorded`; confirm the client can discover that path. The `agent/` directory and `skills-lock.json` are Skill installation metadata, not MCP server configuration.

If the skills CLI does not support the current client, use that client's documented Skill import mechanism when available and report that automatic refresh targeting could not be recorded. A Skill failure does not prevent MCP authorization when the client can still launch local stdio MCP servers. Continue in that case and report the Skill as unavailable. If the client supports neither Skills nor local stdio MCP but can execute commands, continue through Layer D; stop only for Layer E.

## 4. Authenticate with WeChat

For local stdio MCP (Layers B/C), connection can also come before login: configure the current Agent using section 5, then use the bridge's `shiliu_login` tool to display the QR and `shiliu_login_poll` with the returned `login_session_id` as `session`. Poll at the returned interval until success. The bridge completes initialize without credentials and initially exposes three login/status tools. Successful MCP initialize is not proof of login or a remote business connection. Never block QR login on the availability of business tools. The CLI flow below remains supported.

After login, the bridge announces `notifications/tools/list_changed` and adds the remote business tools. Refresh tools/list; if the client does not handle the notification, refresh or reconnect its MCP entry. External CLI login is also detected by the running bridge. Direct HTTP MCP still requires credentials; this guide does not introduce anonymous HTTP business access.

Run `shiliu status`. Reuse working authentication. Log in only when credentials are absent or explicitly rejected; a network failure alone does not justify logout.

```text
shiliu login --no-wait --json
```

Read `qr_code_path`, `qr_code_mime_type`, `user_code`, `poll_command`, `poll_after_seconds`, and `expires_in`. Poll responses may also include `authorization_stage` as `waiting_for_scan`, `processing_callback`, or `expired`. Display the existing local PNG through the current client's human-visible image capability. Agent-side image reading does not prove that the user can see it. Do not recreate or upload the QR, and do not open `verification_uri` as a normal webpage.

Tell the user only: use WeChat to scan the displayed QR code. There is no confirmation button on the phone. Do not wait for the user to reply that scanning is complete.

Immediately run the exact returned `poll_command`. It is a single-shot command. If it returns `authorization_pending`, wait `poll_after_seconds` and run the returned command again. Continue until success, rejection, expiry, a non-retryable error, or the reported `expires_in` reaches zero. Do not use the blocking `--wait` mode in the Agent installation flow. Give the user a progress update at least once per minute.

Track one active login session. Re-running `login --no-wait` must reuse an unexpired local session; do not create duplicate pollers or display an older QR image.

| JSON status | Action |
| --- | --- |
| `success` | Continue to Step 5. |
| `authorization_pending` | Wait the returned interval and poll the same session again. |
| `slow_down` | Use the increased interval and poll the same session again. |
| `expired` | End this session; create at most one replacement and clearly identify its new image. Stop if it also expires. |
| `rejected` | Stop authorization and report rejection. |
| `network_error` | Report the network failure without credentials; do not infer success or replace the session automatically. |
| `error` | Report the returned error and stop unless its action is explicitly recoverable. |

Pending does not prove a callback fault. Deleting a PNG does not revoke its server session.

## 5. Configure the current Agent

Choose the branch established in Step 1.

For Layer B, use the `MCP_AGENT` value from the mapping table:

```text
shiliu install --agent MCP_AGENT --json
```

Configure only the current client. Built-in adapters support Codex, Claude Code, and Cursor. For another safe name, the CLI may return `configuration_generated` with credential-free stdio configuration; `generated_only` means it was not written into the client.

For Layer C, run both commands separately:

```text
shiliu install --agent SAFE_CLIENT_NAME --json
shiliu doctor --transport stdio --json
```

Read `stdio_launch.remote_connected`, `login_state`, `bootstrap_tool_count`, and `business_tool_count` when present. A successful local handshake with only three bootstrap tools means MCP connected but login/business access is not ready; continue QR login instead of reporting installation failure. `shiliu status` and `shiliu tools` must still pass after login.

For `Connection closed`, initialize timeouts, or another connection failure, follow Section 7 before choosing a remedy. Collect the current Agent's actual launch context and safe diagnostic fields; do not infer a login failure from a generic connection error.

Keep `standard_npx` as the preferred candidate. If diagnostics also return `absolute_current_install`, present it only as a fallback and preserve all reported tradeoffs: the path may fail after a runtime/application update, it pins the installed CLI version, and it may require reinstalling the CLI and updating the configuration. `doctor` tests this machine's candidate command, not the target client's process environment.

Before enabling the MCP entry, verify the actual launch context. A terminal global installation and an Agent's application-bundled npx installation can differ. For a client-documented JSON configuration with an empty env, pass that file, the client's actual Node executable, and its npm cache. Paths below are placeholders, not commands to run verbatim:

```text
shiliu doctor --launch-file "CLIENT_MCP_JSON" --node-path "CLIENT_NODE_ABSOLUTE_PATH" --npm-cache "CLIENT_NPM_CACHE_ABSOLUTE_PATH" --prepare --json
```

--prepare warms the same unversioned package in the selected Node/npm/cache before starting the handshake timer, so first-time download/extraction does not consume the MCP initialize deadline. It is opt-in and may install/update that package; omit it for the initial diagnosis of an existing failure. --dry-run never prepares or launches. A successful preparation/version check still requires the subsequent real handshake.

If there is no readable documented configuration file yet, use the same package spec with the client's Node and same-source npm-cli.js:

```text
shiliu doctor --node-path "CLIENT_NODE_ABSOLUTE_PATH" --npm-cli "CLIENT_NPM_CLI_JS_ABSOLUTE_PATH" --npm-cache "CLIENT_NPM_CACHE_ABSOLUTE_PATH" --prepare --json
```

Do not guess private runtime paths or edit opaque application storage. The launch-file reader accepts only standard credential-free Shiliu stdio command/args; it rejects token-bearing env, URLs, headers, and arbitrary command arguments. Read validation_scope and stdio_launch.child_runtime when present. Specified launches do not fall back to a different healthy installation. A successful specified-context probe still does not prove the client has loaded that configuration; reconnect and check native tools in Step 6.

doctor, repair, and --version load only Node built-ins before any SDK/business dependencies. Runtime failures retain exit 3 / RUNTIME_UNAVAILABLE and add a safe runtime.reason, such as DEPENDENCY_INCOMPLETE or NODE_VERSION_UNSUPPORTED, plus actual node_path, node_version, install_root, package_version and whitelisted missing_module/original_error_code. Do not infer that Node 22 is unsupported from a missing Ajv file, or that a repeated login can fix a dependency failure.

For a confirmed damaged extraction directory only: disable this client's Shiliu MCP auto-start first, then run the following dry-run and repair separately. Use the same Node/npm/cache that failed, not an unrelated terminal runtime. CACHE_ENTRY must be the exact reported cache/_npx/HEX directory. Resolve it from child_runtime.install_root or the client's stderr; never repair based on a guessed hash.

```text
shiliu repair --cache-entry "CACHE_ENTRY_ABSOLUTE_PATH" --node-path "CLIENT_NODE_ABSOLUTE_PATH" --npm-cli "CLIENT_NPM_CLI_JS_ABSOLUTE_PATH" --npm-cache "CLIENT_NPM_CACHE_ABSOLUTE_PATH" --dry-run --json
shiliu repair --cache-entry "CACHE_ENTRY_ABSOLUTE_PATH" --node-path "CLIENT_NODE_ABSOLUTE_PATH" --npm-cli "CLIENT_NPM_CLI_JS_ABSOLUTE_PATH" --npm-cache "CLIENT_NPM_CACHE_ABSOLUTE_PATH" --launch-file "CLIENT_MCP_JSON" --json
```

repair requires an exclusive cache entry whose root dependencies contain only @bigbrain-work/mcp-connect. It rejects unsafe/linked paths, another repair lock, and active or unresolved Shiliu launches that could use this entry. It moves only that extraction directory into cache/.shiliu-mcp-backups, reinstalls the original unversioned package spec once, and verifies both the fresh entry and the selected launch via initialize + tools/list. It preserves credentials and other extraction entries and never clears the npm content cache; npm may refresh its content cache normally during installation. CLI processes with this repair guard respect the lock; old clients/old CLI copies may not, which is why disabling auto-start remains required. No infinite retry or whole-cache deletion is performed. Interrupted repairs retain the lock for manual inspection; never remove it while its owner is running. A failed reinstall retains the backup and reports failure; no corrupted backup is silently restored. After repaired, honor reload_required and reconnect the client; don't equate repaired with native Agent access. Keep the evidence backup until recovery is confirmed.

For a GUI, provide these separate fields: server name `shiliu_mcp`; transport `STDIO`; command from the chosen candidate; each `args` value as a separate ordered argument; environment variables empty. Do not add extra quote characters around paths with spaces. The user must save the GUI configuration; do not edit opaque application databases.

For Layer D, do not configure MCP. Use `shiliu tools --json` to read live schemas and `shiliu call TOOL --args-file INPUT.json`. Use `--dry-run` for schema validation without a business call, and use optional `--out RESULT.json` when a large paid response should remain available locally. Do not invoke package-internal `bin/shiliu.js` paths and do not implement JSON-RPC manually.

For Layer E, stop and report unsupported. Do not present a CLI command the client cannot execute.

Inspect `configuration_state`, `config_path`, and `reload_required`. Preserve unrelated settings. Reload or reconnect the client when required. When `reload_required` is true, `configured but awaiting reload` is the normal result for the current session; do not require that same session to discover the newly written MCP connection, and do not report it as `Agent connected` yet. Do not report Agent access while configuration is only generated.

On Windows, keep the generated `cmd /d /s /c npx ... mcp` stdio definition. Do not replace it with `shiliu.ps1 mcp`; npm's PowerShell wrapper may buffer piped input and is not a reliable duplex MCP transport.

## 6. Verify and report

For Layers B and C, run separately:

```text
shiliu status
shiliu tools
```

Require authenticated CLI connectivity and a successful live `tools/list`. When no reload is pending, also confirm that the current Agent has loaded its MCP connection and can discover the live tools. When a reload is required, report `configured but awaiting reload` as the expected installation result and tell the user to reload or reconnect the client before Agent-side discovery can be verified. Do not assume a fixed tool count or run billable business tools solely for installation testing.

For Layer D, successful `shiliu status`, `shiliu tools --json`, and a non-billable `shiliu call TOOL --dry-run` establish `CLI ready`; they do not establish an MCP connection. For Layer C, a successful `doctor` establishes `stdio_launch_verified` only on this machine; it does not establish `Agent connected`.

Report the CLI version, Skill path and scope, configuration state and location, reload state, CLI connection result, Agent connection result, and discovered tool names. Distinguish `CLI ready`, `configured but awaiting reload`, and `Agent connected`. If Agent discovery cannot be verified, say so. Continue the original task using only capabilities actually available.

For an existing connection failure, use Section 7 of this public guide. The installed Skill's `references/installation.md` may provide additional context, but a working MCP connection or installed Skill is not required to read these diagnostics. Update policy belongs to `SKILL.md`, not an extra installation stage. Do not use logout or an unscoped Skills update as generic troubleshooting.

## 7. Diagnose and recover a failed connection

This is an Agent-facing recovery procedure for an existing installation, not a request to repeat all installation steps. `MCP error -32000: Connection closed` and initialize timeouts are symptoms, not diagnoses. Keep the user's original task and resume it only with capabilities that are actually available.

### 7.1 Establish the failed stage before changing anything

Identify whether failure occurs before the CLI starts, during local stdio initialize, while checking login, while connecting to the remote service, or only while loading tools into the Agent. Record the current Agent's documented MCP command/args, transport, Node executable/version, npm-cli.js, npm cache, and configuration source when accessible. A healthy terminal installation may differ from the installation launched by the Agent. Do not guess private runtime paths or modify opaque application storage.

For local stdio (Layers B/C), run these separately and record each exit code. On Windows PowerShell, use `shiliu.cmd` if its `.ps1` wrapper is blocked:

```text
shiliu --version
shiliu doctor --transport stdio --json
```

CLI 1.3.11 or newer is required for independent dependency diagnostics and targeted repair. If older, update only the CLI using Step 2, then resume this recovery procedure; do not reinstall Skills, overwrite other MCP entries, or require login just to diagnose stdio. `--version` alone does not check dependencies. First inspect an existing failure without `--prepare`; preparation may download/update the package and is a separate recovery action.

If the Agent uses another runtime or cache, repeat doctor with that verified context and, when available, its documented credential-free JSON configuration:

```text
shiliu doctor --node-path "CLIENT_NODE_ABSOLUTE_PATH" --npm-cli "CLIENT_NPM_CLI_JS_ABSOLUTE_PATH" --npm-cache "CLIENT_NPM_CACHE_ABSOLUTE_PATH" --json
shiliu doctor --launch-file "CLIENT_MCP_JSON" --node-path "CLIENT_NODE_ABSOLUTE_PATH" --npm-cli "CLIENT_NPM_CLI_JS_ABSOLUTE_PATH" --npm-cache "CLIENT_NPM_CACHE_ABSOLUTE_PATH" --json
```

Choose the applicable command; all uppercase values are placeholders to resolve from evidence, never values to run literally. Read `validation_scope`, candidate `verification`, `stdio_launch`, and `stdio_launch.child_runtime` when present. The cause is in `child_runtime.reason` for a captured runtime failure; some preparation failures use `error_reason` instead. Also inspect `error_code`, `error_stage`, and `process_exit_code`. Do not replace a failed specified-context probe with a successful terminal fallback and call the client repaired.

Use Shiliu's safe log at `~/.shiliu-ai/logs/mcp-diagnostics.jsonl` and the client's captured child stderr if needed. Match timestamps and the actual installation path. `shiliu_connection_status`, when available, reports the diagnostic path and log availability; do not require that tool when initialize itself fails. Extract only relevant safe diagnostic fields, not complete credential stores, environment variables, headers, or unsanitized client logs.

### 7.2 Choose the remedy from evidence

| Evidence | Agent action |
| --- | --- |
| Command execution blocked before `shiliu` starts, no Node/npm, or the client has no local stdio capability | Handle the current client's execution/capability issue through its documented mechanism. Report what could not run. Do not disable built-in security hooks or treat this as a Shiliu login/cache fault. Follow Layers A/D/E as supported. |
| Exit 2 / `CONFIG_INVALID`, or wrong command/args/transport | Compare with the generated Shiliu stdio definition and correct only this MCP entry through the client's documented mechanism. Preserve other entries and credentials. |
| Exit 3 / `RUNTIME_UNAVAILABLE` with `DEPENDENCY_INCOMPLETE`, or captured missing-module evidence in the actual Shiliu installation | Identify the exact failed install. For an exclusive Shiliu `_npx` entry, use 7.3. For a damaged global install, update/reinstall the official CLI in that runtime. Missing Ajv files do not imply that Node 22 is unsupported. |
| `NODE_VERSION_UNSUPPORTED` | Correct the actual launching Node runtime to the CLI's declared minimum. Use Step 1's higher minimum only when a Skill install/refresh is also needed. |
| `NATIVE_DEPENDENCY_UNAVAILABLE` or `RUNTIME_LOAD_FAILED` | Inspect actual OS/architecture/runtime, install path, and the safe original error code. Reinstall the matching official CLI where evidence supports it. Do not assume a dependency-cache repair or repeated scan will fix every runtime failure. |
| Initialize timeout with evidence of first-time npm download/extraction, or `NPM_PREPARE_FAILED` | Check registry/network and the selected runtime/cache. When appropriate, run the same doctor command with `--prepare` once to finish download/extraction before the handshake deadline, then verify initialize + tools/list. Do not blindly loop retries. |
| `REPAIR_IN_PROGRESS`, `REPAIR_ALREADY_RUNNING`, or `MCP_STILL_RUNNING` | Wait for the active repair or stop this Shiliu MCP entry through the client before repair. Never remove a live owner's lock or terminate unrelated Agent/Node processes. An interrupted lock requires manual inspection. |
| Local initialize succeeds, three bootstrap tools, `LOGIN_REQUIRED` or `login_required` | MCP is connected; authentication is pending. Use Step 4's QR login, then refresh tools/list. Do not repair the cache merely because business tools are absent. |
| `AUTH_EXPIRED` | Run `shiliu status` or `shiliu_connection_status` to check/refresh stored authorization. If explicitly rejected or still expired, use Step 4 to log in again; never insert a token into MCP configuration. |
| `CREDENTIAL_UNAVAILABLE` | Check whether CLI and MCP share the same OS user and accessible system credential store. Do not clear credentials as a generic fix. |
| `REMOTE_UNAVAILABLE` | Check remote reachability/network and retry status after recovery. Preserve login and MCP configuration; a network failure does not establish that authorization is invalid. |
| Doctor passes in the actual launch context but native Agent tools remain absent | Check this MCP entry's enable/trust state through the current client's documented UI, then reconnect/reload and verify native discovery. A local probe does not prove the Agent loaded the entry. |
| `PROTOCOL_ERROR` | Check the documented transport and duplex stdio launch, including the Windows cmd definition in Step 5. Preserve protocol stdout; do not add debugging text there. |
| Exit 4 / `INTERNAL_ERROR`, or unresolved failure after the matching remedy | Reconnect once if appropriate, then report safe version/runtime/stage/error evidence for support. Do not claim a root cause without evidence or repeatedly reinstall/scan. |

Fatal startup exits are 2/3/4; normal shutdown is 0. Login, authorization, credential, and remote-network states normally keep the local bridge connected. Distinguish those states from a fatal startup failure.

### 7.3 Repair only a confirmed damaged extraction

Use the exact cache entry resolved from the failed child installation or captured stderr, not a path or hash copied from another user's machine. Confirm that its root manifest belongs exclusively to `@bigbrain-work/mcp-connect`. First stop/disable this entry's automatic launch through the client, then run the repair dry-run and actual repair separately using the same verified Node/npm/cache, as shown in Step 5.

Require dry-run success before repair. Keep the backup, credentials, other package entries, and npm content cache. Repair reinstalls the original unversioned package once and verifies both the rebuilt entry and the selected launch. If reinstall/verification fails, report the error and retained backup; do not delete the whole cache, silently restore the damaged directory, remove a live lock, or retry indefinitely. If `status=repaired`, require both verification results to pass and honor `reload_required`; the client still needs to reconnect.

### 7.4 Reconnect, verify, and report to the user

After the matching remedy, reconnect/reload the Shiliu entry when needed. For stdio, verify initialize + tools/list in the actual launch context. If not logged in, three bootstrap tools are a valid connected state; then complete QR login as needed. After login, run `shiliu status` and `shiliu tools` separately and check whether the current Agent itself can discover the live tools. Never assume a fixed tool count or call paid business tools solely to test recovery.

Report: CLI version; diagnosed stage and safe error code/reason; whether the tested runtime/cache is the Agent's actual context or only the terminal; what was changed; backup path if any; local handshake result; login/remote state; and native Agent discovery/reload state. If commands or configuration cannot be inspected, explain that limit and give only the minimal applicable commands or documented GUI action. Distinguish `diagnosis incomplete`, `local launch verified`, `repaired but awaiting reconnect`, and `Agent connected`; do not mark the user's original task complete from a terminal-only test.
